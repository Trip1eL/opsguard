# OpsGuard 开发路线图

## 目标

围绕一条可重复演示的安全运营垂直链路逐步开发：

```text
多源日志 -> 标准事件 -> 异常行为 -> 行为链 -> ATT&CK -> Sigma 规则
          -> 沙箱验证 -> 审批 -> 灰度/回滚 -> 反馈优化
```

每个模块都先使用确定性实现和固定 fixture 跑通，再接入模型或外部基础设施。Agent 负责理解、规划和解释，核心安全判定、权限门禁和策略生命周期由代码控制。

## 模块总览

| 编号 | 模块 | 主要产物 | 依赖 |
|---|---|---|---|
| M0 | 工程基线 | 环境、配置、日志、测试、CI 约定 | 无 |
| M1 | 事件模型与数据集 | 标准事件模型、三类日志 fixture、标签 | M0 |
| M2 | 日志归一化与检索 | Parser、Normalizer、内存/文件检索接口 | M1 |
| M3 | 异常检测 | 规则检测器、风险分数、告警模型 | M2 |
| M4 | 行为关联与图谱 | 时间线、行为链、Neo4j adapter | M2、M3 |
| M5 | ATT&CK 知识与映射 | 技术库、证据映射、覆盖分析 | M4 |
| M6 | Multi-Agent 调查编排 | Orchestrator、专项 Agent、工具白名单、trace | M2-M5 |
| M7 | 检测策略生成与沙箱验证 | Sigma 生成器、规则执行器、评估指标 | M5、M6 |
| M8 | 响应审批与策略生命周期 | 风险分级、审批、灰度、回滚、模拟响应 | M3、M7 |
| M9 | 反馈飞轮与展示层 | 反馈闭环、优化建议、API 和可视化 | M6-M8 |

## 模块定义与验收标准

### M0：工程基线

范围：Conda 环境、`pyproject.toml`、配置加载、结构化日志、测试目录、Git 工作流和 Docker Compose 基础配置。

验收：新机器执行环境安装命令后可以导入包；测试、lint 和基础服务检查有明确命令；敏感配置只从 `.env` 读取且不会进入 Git。

### M1：事件模型与数据集

范围：统一 `Event`、`Alert`、`Case`、`Evidence` 等领域模型；准备 Linux SSH/audit、Web access、process/network 三类 JSONL fixture，覆盖两类可疑行为和一类正常发布行为。

验收：每条 fixture 可以被 Pydantic 校验；每个案例有事件标签、实体标签和预期行为阶段；数据集可重复生成，原始日志和标准事件可以互相追溯。

### M2：日志归一化与检索

范围：为三类日志实现 parser 和 normalizer；定义 `EventRepository` 接口，先实现文件/内存 adapter，后续再接 Elasticsearch/OpenSearch；支持时间、主机、用户、进程、IP 和域名过滤。

验收：同一案例的多源日志可以统一查询；查询结果保留 `event_id` 和原始日志；非法字段、时间格式和未知事件类型有明确错误处理。

### M3：异常检测

范围：先实现确定性检测器，包括异常登录、稀有外联、解释器异常启动、计划任务持久化和 Web 进程异常子进程；输出告警、风险分数和命中证据。

验收：三个案例均能产生预期告警；正常发布案例不会因为批量登录或批量脚本执行直接判为高风险；检测器可单独测试，不依赖 LLM。

### M4：行为关联与图谱

范围：实现时间窗口、实体聚合、父子进程和因果边推断；输出 `BehaviorChain`；定义 Neo4j adapter，先用内存图验证查询，再接 Docker Neo4j。

验收：可以从一个告警还原至少一条完整行为链；链上每个节点都能回溯到事件；能够查询账号、主机、进程和外联域名的关联关系。

### M5：ATT&CK 知识与映射

范围：引入版本化的 ATT&CK 子集，覆盖项目案例所需技术；实现规则/证据优先的映射器，并保留技术编号、名称、证据事件和置信度。

验收：案例行为链可以输出稳定的 Technique Mapping；映射结果有证据引用和置信度；可以统计每项技术的检测规则覆盖情况。

### M6：Multi-Agent 调查编排

范围：实现 Orchestrator 和 Investigation、Correlation、Mapping、Detection、Validation、Response、Evaluation Agent 的协议；使用 LangGraph 或现有状态机串联工具；记录每次工具调用和失败重试。

验收：输入一个自然语言调查问题可以完成 M2-M5 的流程；Agent 只能调用白名单工具；工具超时、空结果和结构化输出错误可以分类处理；最终输出调查报告和证据链。

### M7：检测策略生成与沙箱验证

范围：根据行为链生成 Sigma 规则；实现字段和语法校验、规则版本、Docker/离线回放执行器；计算 Precision、Recall、F1、误报率和执行延迟。

验收：至少一个可疑案例能生成并命中 Sigma 规则；正常发布案例可验证误报；验证失败时能返回具体样本和调整建议；规则不会访问生产数据或执行任意命令。

### M8：响应审批与策略生命周期

范围：实现风险分级、人工审批、模拟隔离主机/禁用账号/阻断域名；实现规则 `DRAFT -> VALIDATED -> CANARY -> ACTIVE -> ROLLED_BACK` 状态和审计记录。

验收：未经审批不能执行高风险响应或正式发布；灰度指标超过阈值会自动暂停并回滚；每次审批、执行和回滚都可追溯。

### M9：反馈飞轮与展示层

范围：采集人工标注、误报/漏报、规则指标和 Agent trace；生成候选规则优化版本；提供 FastAPI API 和最小前端，展示告警、行为图、ATT&CK、规则验证和审批状态。

验收：一条规则的反馈可以触发候选新版本；新旧版本可以离线对比；前端能完成一次调查结果查看和规则审批演示；Docker Compose 可以启动完整演示链路。

### M10：真实模型与可观测性

范围：通过 OpenAI-compatible 中转网关接入真实 LLM，让模型输出受 Pydantic
约束的调查目标、过滤条件、关注实体和建议工具链；执行参数继续经过 allowlist，
检测、验证、审批和响应仍由确定性代码控制。使用 LangSmith 记录模型、Token、延迟、
结构校验和 Trace ID，并强制隐藏原始输入输出。

验收：真实模型计划可以驱动一次完整 fixture 调查；非法字段和乱序工具被拒绝；
模型或观测服务失败时自动回退确定性链路；测试不读取真实密钥或产生模型费用；
LangSmith 能查询根调查 Run 和模型子 Run，且 Trace 不包含问题、Prompt、计划正文或密钥；
工作台在桌面和移动端展示计划与观测指标。

### M11：Agent Eval 与安全红队评测

范围：建立正常、提示注入、越权攻击、空结果、模糊问题、模型超时和非法 JSON 用例；
统一计算结构有效率、过滤器依据性、工具白名单、审批绕过、敏感数据泄露、故障降级、
延迟、Token 和成本指标。提供免费 fixture 模式与受 case/Token 预算约束的 live 模式。

验收：fixture 评测可在 CI 中零费用复现；安全不变量全部达到硬门禁，质量指标达到
版本化阈值；报告只包含 case ID 和脱敏指标，不写入 Prompt、模型原始输出、日志或密钥。

## 开发顺序

建议按以下顺序逐个开发，每完成一个模块就提交一次：

```text
M0 -> M1 -> M2 -> M3 -> M4 -> M5 -> M6 -> M7 -> M8 -> M9 -> M10 -> M11
```

M4 的 Neo4j、M6 的模型调用和 M9 的前端都可以先用 adapter 或 mock 实现，不能阻塞主链路。每个模块都要补齐单元测试；M2 之后增加集成测试，M7 之后增加端到端演示测试。

## 第一阶段里程碑

第一阶段只做到 `M0-M3`：能够加载三类模拟日志，归一化为统一事件，识别异常行为并输出带证据的告警。这是后续 Agent、图谱和规则生成的稳定数据基础。

第二阶段做到 `M4-M6`：能够从告警还原行为链，映射 ATT&CK，并由 Multi-Agent 根据自然语言问题完成调查报告。

第三阶段做到 `M7-M9`：补齐规则生成、沙箱验证、审批、灰度、回滚、反馈优化和可视化，形成可展示的完整闭环。

第四阶段完成 `M10`：在不削弱确定性安全门禁的前提下接入真实模型规划、结构化
输出校验、失败降级和隐私保护的 LangSmith 可观测性。

第五阶段完成 `M11`：用版本化 Agent Eval 和安全红队样例验证模型质量、系统韧性与
安全边界，并把阈值固化为可自动执行的发布门禁。

第六阶段完成 `M13`：将 LangGraph 接入默认调查编排，提供 OpenSearch 事件仓储、
Neo4j 图存储和 Docker 规则回放 Worker；保留 JSONL/内存/进程内实现作为个人项目的
可重复 fallback，并通过环境变量切换后端。
